## 原因判断与仍未知的部分

现有证据支持：失败发生在请求体传输/接收阶段，尚未完成正常的收货处理流程。
它不是“照片已进数据库，只是模型识别了几个小时”的证据。

检查时两层生产 Nginx 的请求体超时均为 120 秒，且均关闭请求体代理缓冲。
Nginx 的 `client_body_timeout` 是两次读取之间的空闲时间；持续没有数据会导致 408。
Nginx 源码也会在读取请求体时遇到连接提前关闭或读取错误后返回 400；相关提前关闭消息为
INFO 级，现有较高日志级别不一定保留它。
参见 [Nginx 请求体超时文档](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_body_timeout)
和 [请求体读取实现](https://github.com/nginx/nginx/blob/master/src/http/ngx_http_request_body.c)。

但旧日志没有请求总耗时、已接收长度、请求声明长度或浏览器端阶段信息，因此还不能断言：

- 是 Safari/IndexedDB Blob 读取或序列化异常，还是网络/页面生命周期中断；
- 每次失败传到了多少照片字节；
- 手机里每一个旧 Blob 是否仍可完整读取。

没有证据表明此事故由照片超大、照片格式不支持或服务器磁盘写满造成。
生产 Nginx 上限为 16 MiB，应用上限为 12 MiB；近期成功保存的照片均小于 0.9 MiB。
检查时磁盘剩余约 24 GiB、本机健康检查约 6 毫秒。后两项是检查当时的快照，不代表事故时的资源监控。

视觉模型配置为 `glm-4.1v-thinking-flash`、12 秒网络超时。9 月 7 日的 97 次成功请求，
按时间顺序配对数据库“上传校验结束”时间与后端 201 日志，后续处理阶段约为中位数 9 毫秒、
95 分位 7.15 秒、最大 8.12 秒。这只是近似配对，**不包含照片传输时间，也不是精确的请求耗时**。
提高模型超时不能修复尚未完整到达服务器的照片。

## 安全恢复与连续拍摄边界

出现“本机待上传”时，先保留原来的手机、同一个浏览器和网站地址：

1. 不清理浏览器缓存/网站数据，不删除本机队列，不切换到无痕模式，不卸载应用。
   服务器没有保存成功的照片可能只剩 IndexedDB 里的这一份。
2. 保持原页面打开并停留在前台，使用稳定网络重试；先确认队列数下降、收货记录里出现照片，
   再判断恢复成功。切换账号前先核对队列归属，不把其他操作人的本机照片归到当前账号。
3. 如提供“导出/下载原图”的恢复入口，先保存可读取的原图；若照片读取明确失败，保留记录和错误信息，
   有相册原图时再重新选择。不要先清空队列再尝试恢复。

连续拍摄允许在当前照片已经持久化到本机后继续拍下一张，不需要等待此前照片上传完毕。
但网页不能保证锁屏、切后台、关闭标签页之后继续上传；“本机已保存”与“服务器已同步”必须分开显示。
前台队列采用重试定时器和回到前台/恢复网络后的检查，并对读取、准备、上传分别设截止时间，
失败项继续保留，避免一个挂起任务永久占用整条队列。本地条码识别 Worker 上限 5 秒，
照片字节读取上限 15 秒，照片准备上限 20 秒（超时回退至已保存原图），收货请求上限 60 秒。
对应参数以 `uploadQueue.ts`、`barcode.ts`、`photoCopy.ts`、`preparePhoto.ts` 和 `api.ts`
中的实现为准；定时器不是后台上传服务。

调度优先让尚未尝试的照片进行首传，再按重试到期时间轮转。否则两张慢失败照片可能一直交替
重试，使后续照片得不到处理。只对可判定的传输故障自动重试（包括收货接口返回的空/HTML 400）；
JSON 400 等明确校验失败不会无限自动重试。旧版已标记永久暂停的记录，更新页面后可点击顶部
「失败」或「待上传」计数一次性继续同步；不需要重新拍摄或逐张补录。

## 新增的隐私安全上传日志

`deploy/nginx/default.conf.template` 对规范化路径 `/api/receipts` 使用独立 JSON 日志格式。
**生产 Compose 实际将此文件只读挂载到前端容器模板目录，覆盖镜像自带的模板。**
`frontend/nginx/default.conf.template` 同步保留相同日志设置，供没有该生产挂载的镜像使用。
两者都写入镜像既有的 `/var/log/nginx/access.log`，其他 API 路径沿用原来的 `main` 格式。
此路径的 GET 与 POST 都可记录，分析上传时按 `method=POST` 筛选；不会同时生成两份诊断日志。

诊断字段包括：时间、随机请求 ID、方法、无查询参数的路径、状态码、请求声明长度、实际读取的
请求总长度、请求总耗时、上游状态和上游响应耗时。不记录照片、请求体、Cookie、Authorization、
运单号、IP、User-Agent 或查询参数；这只描述新增格式，不改变其他既有访问日志的数据范围。

注意：

- `request_length` 包含请求行、请求头和请求体，不是纯照片字节数。
- `content_length` 可能为空，`upstream_status` / `upstream_response_time` 也可能为空或包含多个值，
  因此这些字段以 JSON 字符串记录。所有字符串均使用 JSON 转义。
- 前端容器日志看不到在外层 Nginx 就被终止、未转发到容器的请求。如需覆盖此类失败，可在外层
  Nginx 同样增加只针对收货路径的安全格式。这是后续运维选项，不是本次已做的生产修改。
- 模板由官方 Nginx 镜像入口处理；手工替换模板时只替换 `${BACKEND_URL}`，不要把 Nginx 的
  `$uri`、`$request_time` 等变量误当环境变量全部替换为空。
- 镜像内 `frontend/nginx` 的简化模板与生产硬化配置不同；发布必须使用 `deploy/nginx` 模板。
  本次改动前，仓库 `deploy/nginx` 模板与线上挂载文件逐字节一致；此次只增加日志格式、条件映射
  和两条访问日志指令，保留原有代理、CSP、安全头、超时、上传上限与 Docker DNS 设置。
  不修改宿主机 TLS 配置。模板变更应先用目标镜像执行 `nginx -t` 验证，再只重建前端服务。
